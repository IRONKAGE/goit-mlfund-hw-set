## 🤼‍♂️ ФП: Прогнозування відтоку клієнтів (Customer Churn Kaggle Challenge)

### 🎯 Опис задачі

Головна мета фінального проекту — розробка предиктивної моделі для ідентифікації клієнтів телекомунікаційної компанії, схильних до відтоку (Customer Churn).
Задача зводиться до **бінарної класифікації** на високорозмірному наборі даних: 10 000 об'єктів та 230 ознак (з яких 190 — числові, а 40 — категоріальні). Головні ускладнення набору даних:

- **Жорсткий дисбаланс класів** (~13% позитивного класу)
- **Висока кардинальність** категоріальних ознак та критична кількість пропусків (NaN)
- **Метрика оцінювання:** Збалансована точність (Balanced Accuracy), яка штрафує модель за ігнорування міноритарного класу

---

### 🧮 Математичне ядро: Пайплайн зі SMOTE та Градієнтним Бустингом

У процесі дослідження ми розробили Production-ready конвеєр, який вирішує проблеми брудних та незбалансованих даних:

1. **Балансування класів: Синтетична генерація (SMOTE)**
    Для боротьби з жорстким дисбалансом було застосовано класичний алгоритм `SMOTE`. Він генерує синтетичні зразки міноритарного класу за допомогою лінійної інтерполяції між сусідами:
    $$x_{new} = x_i + \lambda \times (x_{zi} - x_i)$$
    де $\lambda \in [0, 1]$. Щоб уникнути витоку даних (data leakage) під час крос-валідації, алгоритм `SMOTE` було жорстко інтегровано безпосередньо у конвеєр `ImbPipeline`, що гарантує генерацію даних виключно на тренувальних фолдах

2. **Обробка пропусків та Кодування (Imputation & OHE)**
    Для вирішення проблеми критичної кількості пропусків (NaN) було використано `SimpleImputer`. Числові ознаки відновлювалися за медіаною (`strategy='median'`), а категоріальні — за найчастішим значенням (`strategy='most_frequent'`) перед застосуванням `OneHotEncoder` або передачею у нативні бустинги

---

### 🧪 Квантова пояснюваність (SHAP) та Калібрування порогів

Замість сліпого використання моделі як "чорної скриньки", ми імплементували глибоку математичну аналітику:

1. **SHAP (Shapley Additive exPlanations)**
    Для пояснення прогнозів ансамблів використано вектори Шеплі з теорії кооперативних ігор. Вплив кожної ознаки $i$ розраховується як її маргінальний внесок у всі можливі комбінації ознак $S$:
    $$\phi_i = \sum_{S \subseteq N \setminus \{i\}} \frac{|S|! (|N| - |S| - 1)!}{|N|!} [v(S \cup \{i\}) - v(S)]$$
    Незважаючи на анонімізовані дані, побудова графіка бджолиного рою дозволила виявити найвпливовіші тригери відтоку клієнтів

2. **Cost-Sensitive Thresholding (Симуляція порогів)**
    Стандартний поріг прийняття рішень $t = 0.5$ є субоптимальним для незбалансованих вибірок. Ми провели симуляцію для 100 порогів ($t \in [0.01, 0.99]$), максимізуючи цільову метрику змагання:
    $$BA = \frac{TPR + TNR}{2} \rightarrow \max_{t}$$
    Динамічно знайдений оптимізований поріг (у нашому випадку близько `0.515`) дозволив суттєво знизити кількість хибнонегативних помилок (FN) та максимізувати фінальний Kaggle Score

### 🚀 Advanced MLOps (Production Ready)

Архітектура проекту побудована за стандартами Enterprise MLOps:

- **Smart Caching (Розумне кешування):** Інтегровано систему хешування (`hashlib.md5`) для стану набору даних. Важкі обчислення (Auto EDA) виконуються лише при зміні структури даних, заощаджуючи ресурси
- **Hardware Routing:** Ядро автоматично детектить наявні акселератори (`CUDA`, `MPS`, `XPU`) та маршрутизує тензорні обчислення на відповідний бекенд для досягнення максимальної швидкості
- **MLflow & Secure Serialization:** Моделі логуються у локальну SQLite базу з використанням новітнього формату безпеки `skops` (із розширеним переліком `skops_trusted_types` для підтримки внутрішніх структур бустингів та об'єктів `imblearn`)
- **Human-in-the-Loop (HITL):** Створено реактивний інтерфейс (Marimo) для "Режиму Архітектора", що дозволяє мануально перехоплювати управління після Байєсівської оптимізації (Optuna) для примусової регуляризації (наприклад, зрізання `max_depth` чи `learning_rate`), запобігаючи перенавчанню моделі

### 📊 Результати та Висновки

- **Перемога Бустингів:** Сучасні імплементації градієнтного бустингу (XGBoost, LightGBM, HistGradientBoosting) повністю перевершили базові лінійні моделі та класичний Random Forest на етапі Screening'у
- **Відбір ознак (Feature Selection):** Використання ґрунтованого на алгоритмах відбору (`SelectFromModel` з `XGBClassifier`) дозволило автоматично відсіяти сміттєві вектори перед фінальним навчанням
- **Auto (Optuna) vs Manual (HITL):** Оптимізація гіперпараметрів для максимізації метрики змагання (Balanced Accuracy) проводилася за $n=30$ ітерацій за допомогою алгоритму байєсівської оптимізації `TPESampler`.
  - *Автоматичний режим (Auto):* Модель LightGBM(OHE), оптимізована виключно Optuna, підігнала параметри під крос-валідацію (3-Fold CV). Це дало Public Score **0.8739**, але на прихованих даних (Private Score) результат впав до **0.8706** через перенавчання (Overfitting) на особливостях тренувального набору.
  - *Ручний режим (Manual Override):* Завдяки архітектурі HITL, ми перехопили управління та примусово змінили архітектуру для кращої генералізації. Кожен параметр був скоригований з чіткою інженерною метою:
    - **`subsample=0.8` (було 0.3):** Збільшення частки рядків з 30% до 80% дало деревам достатньо даних для розпізнавання патернів, при цьому зберігши 20% випадковості для боротьби з перенавчанням.
    - **`colsample_bytree=0.75` (було 1.0):** Зниження цього параметра змусило алгоритм на кожному кроці ігнорувати домінантні "шумні" ознаки і знаходити приховані інсайти у слабших векторах.
    - **`max_depth=5` (було 6):** Зрізання глибини зменшило кількість листків, заборонивши моделі зазубрювати дрібні деталі тренувальної вибірки.
    - **`n_estimators=350` та `learning_rate=0.047` (було 150 та ~0.012):** Синхронізація об'єму дерев та швидкості дозволила моделі робити впевнені кроки і гарантовано дійти до глобального мінімуму помилки, уникаючи недонавчання.
  - *Підсумок:* Ця хірургічна інженерна корекція дозволила уникнути зазубрювання і досягти феноменального **Private Score 0.8896** на платформі Kaggle. Мануальний підхід підняв справжню метрику майже на 2%, довівши, що інженерна логіка перевершує сліпий автопошук!
- **Лідерборд:** Загальна стратегія з використанням `SMOTE`-оверсемплінгу, медіанної імпутації та кастомного калібрування порогу (`Threshold Tuning`) дозволила побудувати потужний ультимативний пайплайн і вийти на високий конкурентний рівень

### 📊 Висновки (Академічні вимоги vs Production)

Цей проект яскраво продемонстрував ключові принципи розробки Production-даних:

1. **Витік даних (Data Leakage):** На відміну від спрощених підходів, де синтетичні дані генеруються на всьому наборі даних одразу, Production-рішення вимагає використання `ImbPipeline` для застосування `SMOTE` виключно на тренувальних фолдах під час крос-валідації
2. **Калібрування порогу:** Дефолтний поріг відсічення $t=0.5$ майже ніколи не працює для незбалансованих бізнес-задач. Динамічний пошук ідеального порогу на основі `predict_proba` доводить, що Threshold Tuning є критичним інструментом для максимізації Balanced Accuracy
3. **Оптимізація vs Архітектура:** Алгоритми AutoML та Optuna можуть швидко знайти ефективні гіперпараметри, але без інженерного контролю вони здатні перенавчити модель. Гібридний підхід (Optuna + HITL Manual Override) гарантує, що інженерна інтуїція завжди залишатиметься надійним запобіжником при побудові стійких ML-систем
